# API contract v1

Base URL entered in Android is origin e.g. http://192.168.1.10:56507. All paths below include /api/v1. JSON UTF-8. Bearer opaque token except health/auth. Errors {"error":"human readable Chinese"}. Timestamps RFC3339. IDs strings. Unknown fields rejected for writes. Server owns user identity, recipients and media.

Version 1.8.0 requires both backend and Android to be upgraded for exact reminder windows. Older APKs discard end_at when saving a rule, so they must not create or edit exact windows. Building or installing an APK does not replace or restart an existing backend process.

Registration is open to syntactically valid email addresses. Registration requires a valid email code and creates a password account; it also sets the first password on an existing OTP-only account while preserving its ID, tasks and existing sessions. A password account cannot be overwritten by registration (409); use password/reset with a new valid code. Reset requires an existing account and revokes all its previous sessions before returning a new token. It does not affect other accounts or user data. Code consumption, account/password writes, session revocation and new session creation commit atomically; failed writes/commits leave the code and existing credentials/sessions intact.

Passwords must contain at least 8 Unicode characters and at most 128 UTF-8 bytes. Passwords are never trimmed; email is lowercased and trimmed. Stored password hashes use PBKDF2-HMAC-SHA256, 600000 iterations, independent cryptographically random 32-byte salts, a 32-byte key and a fixed versioned format. Neither responses nor export expose credentials. Incorrect passwords and unknown accounts both return 401 with the same message and incur the same KDF work. Five failed attempts per normalized email in a 15-minute window block further password attempts with 429 until that window expires. Additionally, 30 failures per direct network source in the same window cause 429; forwarding headers do not change the source. Failure windows persist across restarts. A successful password login or verified password setup/reset clears that email's failure window. Password sessions last 90 days; clients normally reuse their token and may reauthenticate with locally encrypted credentials when needed.

The shared code endpoint sends a general account verification code, valid for 10 minutes, with a 60-second resend cooldown and 10 sends per UTC day. Five incorrect code attempts invalidate it across register, reset and legacy verify. Legacy auth/verify remains compatible: first verification creates an OTP-only account, repeated verification reuses it, and password_set reflects whether that account has a password. Legacy allowed_emails configuration remains ignored across login, sessions and reminder delivery. Existing accounts and tokens survive the additive password-table migration.

Rule fields: {"kind":"monthly_window","mode":"until_done","timezone":"Asia/Shanghai","times":["09:00"],"start_date":"2026-10-03","end_date":"","weekdays":[],"month_start":1,"month_end":15,"every_days":0,"max_reminders":0}
kind = once | daily | weekly | monthly_window | date_range | interval | ongoing | minute_interval.
mode = until_done (one completion ends current cycle) | every_day (completion only stops that day's remaining reminders) | notify_once (only first notification each cycle, no completion required).
times: unique HH:mm 1..8 values. weekdays 1=Mon..7=Sun. max_reminders 0 unlimited, otherwise per cycle cap 1..100. once requires start_date, date_range requires both dates, interval requires start_date and every_days (1..365), monthly_window needs month_start<=month_end, 1..31 (clamp end to last actual day; start 31 means last day in short months). Daily repeating kinds honor optional start/end bounds. All use calendar day arithmetic.
ongoing requires start_date, optional end_date, mode=until_done only. Repeats daily until one permanent completion, fixed cycle ongoing:<start_date>. Use this for daily reminders until a one-time obligation is fulfilled with no explicit deadline; daily kind resets completion each day.

minute_interval requires mode=until_done, first_at (RFC3339 timestamp including seconds and Z or an explicit numeric offset), repeat_minutes (integer 1..1440). Example: {"kind":"minute_interval","mode":"until_done","timezone":"Asia/Shanghai","first_at":"2026-10-03T15:15:27+08:00","repeat_minutes":5,"times":[],"max_reminders":0}. First reminder is first_at, subsequent reminders use elapsed minutes anchored to that instant, including across midnight, months and DST. Completion key is the task-scoped constant minute_interval, valid even before the first reminder; one completion permanently stops the task and editing the cadence/anchor/deadline preserves it. max_reminders=0 is unlimited across the entire task. Times, start_date, weekdays must be empty; month_start/month_end/every_days must be zero. Other kinds reject nonempty first_at or end_at and nonzero repeat_minutes. Empty minute fields are omitted during serialization so existing notification snapshots remain compatible.

Minute reminder deadline fields:

| Field | Contract |
|---|---|
| end_date | Optional YYYY-MM-DD; includes the whole final day in the rule timezone. |
| end_at | Optional RFC3339 timestamp including seconds and Z or a numeric offset; fractional seconds allowed. Only valid for minute_interval, must not precede first_at. |
| Mutual exclusion | end_at and end_date cannot both be nonempty. Omit both for no deadline. |

An exact-window rule is {"kind":"minute_interval","mode":"until_done","timezone":"Asia/Shanghai","times":[],"first_at":"2026-10-03T14:00:00+08:00","repeat_minutes":30,"end_at":"2026-10-03T17:00:00+08:00","max_reminders":0}. A cadence slot at end_at is eligible; no reminder is eligible after it. The deadline does not insert an extra slot when it falls between cadence slots. Calendar projection, completion eligibility, snoozing, catch-up and pending retry checks honor the same deadline. Snoozing to end_at is allowed, snoozing beyond it is rejected. Completing within the active cycle stops all remaining reminders permanently.

An exact window with a past first_at may be confirmed only while end_at has not expired and there is still a future cadence candidate. The original deadline and cadence are preserved; creation does not backfill slots from before creation. Fully expired windows and windows without a future candidate are rejected. For a new minute rule without end_at, first_at must still be in the future; editing an existing task may retain its past anchor. Repeating fixed-hour windows every day or every week are not supported.

The scheduler checks every 30 seconds. For minute_interval, restart catch-up selects only the latest elapsed slot (even if just before midnight) and never sends all missed intervals; expired tasks neither catch up nor retry. Successful sends are deduplicated durably; pause, completion, optional cap, archive and snooze still apply. Snooze emits one reminder at its expiry then resumes the original anchor's cadence. Email arrival also depends on the mail provider; a schedule candidate is not a guarantee of delivery at that exact second.

Only the complete mutation response includes growth. Counts are the current user's actual lifetime completion rows for this task; stages use the same thresholds as the garden: 0 seed, 1–2 sprout, 3–6 leaf, 7+ bloom. A newly committed completion returns added=true with counts immediately before and after that write. Retrying an already completed cycle returns the original Completion fields, added=false, and the actual current count/stage in both from and to fields; it never invents an additional growth step. Failed writes or commits return an error without growth. Clients animate only an added=true response; same-stage completions may still show a small growth reaction. History, export, and garden recent_completions keep the unchanged Completion schema. Completing a foreign or archived task remains rejected.

GET /api/v1/garden?timezone=Asia%2FShanghai -> {"timezone":"Asia/Shanghai","generated_at":"RFC3339","week_start_date":"2026-09-28","total_completions":20,"week_completions":3,"total_plants":2,"plants":[GardenPlant],"recent_completions":[Completion],"truncated":false,"plant_limit":2000}
GardenPlant {"task_id":"...","title":"...","completion_count":7,"last_completed_at":"RFC3339 or empty","archived":false,"stage":"seed|sprout|leaf|bloom"}

The authenticated garden endpoint defaults to Asia/Shanghai when timezone is omitted; an invalid, empty, repeated, or implicit Local timezone is rejected with 400. It accepts only the optional timezone query parameter. All-time and current local-week totals count actual completion rows, including archived tasks, independently of the recent-record limit. The week starts Monday at 00:00 in the requested timezone and ends at the next local Monday. Reminder delivery never counts as completion. Repeated completion of the same task cycle remains one stored completion, and skipped days never reduce growth.

Every non-archived task, including paused tasks and seeds with no completions, is a plant; archived tasks remain plants only when they have completions. Plant titles reflect current task titles; recent Completion records retain their historical task_title, text and media_ids. Stages use lifetime completion_count: 0 seed, 1–2 sprout, 3–6 leaf, 7+ bloom. Plants sort with non-archived tasks first, then by latest completion and task creation, and return at most 2,000 items with full total_plants and explicit truncated metadata. recent_completions contains at most the latest 12 actual Completion records. Totals always cover all owned completion records, even when the plant list is truncated. All fields are read from one database snapshot and ownership is checked on both tasks and completions; empty lists are arrays.

GET /api/v1/calendar?month=2026-10&timezone=Asia%2FShanghai -> {"month":"2026-10","timezone":"Asia/Shanghai","generated_at":"RFC3339","entries":[CalendarEntry],"truncated":false}
CalendarEntry {"id":"stable identifier","type":"planned|notification|completion","task_id":"...","task_title":"...","at":"RFC3339","state":"upcoming|pending|completed|expired|notified","cycle_key":"...","cycle_end":"RFC3339 or empty"}. Notification entries retain scheduled_at/sent_at/status/error; completion entries retain created_at/text/media_ids. Planned entries are projections, never persisted notifications and never evidence that mail was sent.

The calendar endpoint accepts one valid YYYY-MM month and explicit IANA display timezone, returns only the authenticated user's entries, and bounds the response at 20,000 entries or a 6 MiB serialization budget, with an explicit truncated flag. Both actual records and projected times are grouped by their instant in that display timezone. Projection uses the same schedule rules as delivery, excludes times before task creation, honors completed cycles, notification caps and snoozing, and suppresses unsent plans for paused/archived tasks. Actual notifications override the projected entry at the same task+instant; actual completions and their text/photos remain available. Every-third-day rules use start_date as their calendar anchor.

Calendar states: upcoming = future reminder; pending = due but its completion cycle has not ended; expired = cycle ended without completion; completed = actual completion or an earlier reminder in a completed cycle; notified = a successful notify_once reminder (no completion required). Mail transport failures do not determine completion or expiry. Historical notifications use their saved rule snapshot; historical completions with no reliable cycle boundary leave cycle_end empty. Unsent past projections use the current rule only from max(created_at,updated_at), conservatively avoiding fabricated history after edits. Future forecasts may change when the user completes, pauses or edits a task.

Android loads the selected month, filters selected days locally, and rejects stale responses after month/account/page changes. Old servers without the endpoint show an explicit update notice instead of pretending an empty calendar is complete; stored records remain unchanged on the server. task_id provides owner-authenticated navigation to the reminder, including read-only archived reminders.

AI parsing is pinned to deepseek-flash with thinking.type=disabled, regardless of legacy model configuration. The model decides completion semantics before cadence: a one-time obligation such as collecting laundry means until_done; "do it once" does not mean "send only one notification". An explicit request for one notification without completion takes precedence. Initial delay and repeat_minutes are separate: "十分钟后收衣服" means first_at is ten minutes later, with a default five-minute repeat for a short household task when no cadence was supplied. A single several-hour window without an explicit cadence defaults to thirty minutes. Added defaults must appear in warnings and remain editable in the draft; explicit user cadence, limits and notification-only instructions take precedence. These are model instructions, not a local numeral-regex parser or rule fallback.

Invalid JSON or invalid draft rules trigger at most one additional AI request with the original text, the same reference time, the rejected draft and validation feedback. Both drafts pass the same strict JSON field/type, title, schedule and future-candidate checks; summary is generated by the backend. The whole parse is bounded to 65 seconds. Provider connection/authentication/balance/rate-limit failures stop without retry or a fabricated draft. An explicit unsupported-rule response is reported directly; a second invalid draft returns a readable failure. Nonempty inputs are limited to 2,000 characters, and the existing per-user parse quota still applies. Unsupported conditions, including daily/weekly repeating fixed-hour windows, must be reported rather than silently dropped.

Scheduler package contract (Go): type Rule matching JSON above; Validate(Rule) error; Summary(Rule) string; CycleAt(Rule,time.Time) (Cycle,bool), Cycle {Key string; Start,End time.Time}; Due(Rule,from,to time.Time) []Occurrence, Occurrence {At time.Time; CycleKey string}; DueLimited(Rule,from,to time.Time,limit int) []Occurrence returns the earliest candidates up to a bound; LatestDue(Rule,from,to time.Time) (Occurrence,bool) uses constant-space arithmetic for minute intervals; Next(Rule,after time.Time) (time.Time,bool). Complete cycle includes day for every_day, otherwise monthly YYYY-MM, weekly ISO year/week, date_range fixed window, or task-lifetime minute_interval. Dates are inclusive; interval is anchored to start_date. Backend checks archived/paused/snoozed/completed cycle plus successful reminder count before enqueue/send. Notification unique(task_id,scheduled_at). Future schedule edits must not resurrect already-sent slots; completion history survives edits. Catchup selects only the latest due slot; fixed-clock rules additionally restrict it to the current local day.
